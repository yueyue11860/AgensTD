# 专项设计：PVP 开发拆分与验收清单

> 本文件是《专项设计-PVP完整玩法与竞技系统.md》的执行索引。  
> 所有模块先遵守总设计，再各自实现；任何协议变更必须同步 shared、BE、FE 和迁移。

## 0. 2026-08-25 实施快照

首轮纵向切片已经完成：独立 PVP 合同、两界斗法台、双侧权威 Runtime、真人匹配与确认、遣妖、终局、赛季/段位/榜单/历史/结算 Store、Supabase 迁移、PVP REST 装配、前端 PVE/PVP 双入口及全部首发页面均已落地，并有 TypeScript、领域 smoke、双真人 HTTP smoke、前端生产构建和浏览器路由验证。

以下仍属于后续生产化任务，不得因为首轮页面和骨架可运行就标记为“完整 PVP 已上线”：

1. 把现有天兵征兵、托盘/备战席/棋盘两两操作、神将、羁绊、武器和道具竞技快照正式接入 `PvpMatchRuntime`；当前战斗切片只验证怪物、核心、真经和权威伤害边界。
2. 用 Socket 按查看者推送增量 Tick、20/60 秒重连和观战延迟；当前前端使用 500ms REST 权威轮询完成联调。
3. 在获批环境实际执行并回滚验证 PVP migration；设置 `PVP_STORE=supabase` 后做并发事务和故障恢复实测。默认 `memory` 仅供本地开发，重启会清空战绩。
4. 把每局 Runtime 事件接入 Replay Manifest/Chunk recorder，并完成跨版本重演；当前已经完成回放存储边界，尚未装配每局 recorder。
5. 运行奖励 Outbox worker，把荣誉/金币以唯一 eventId 接入正式账户 CAS；当前段位已能原子提交，账户奖励仍停在可重试队列模型。
6. 完成教学演练、竞技借用库、正式构筑校验、赛季冻结/归档任务、处罚/举报后台和内容热禁用。
7. 完成正式地图表现、PVP Boss、更多压力命令、观战、2v2 和赛事阶段。

## 1. 共享契约负责人

交付：

- `shared/contracts/pvp.ts`；
- PVP 地图、房间、公开/私有 Tick、动作、结算、段位、榜单、历史类型；
- 明确版本字段和兼容策略；
- 旧 `competition.ts` 进入只读迁移状态。

验收：公开投影不含对手隐藏状态；所有写动作有 requestId、Tick/版本或修订号。

## 2. 地图与权威对局负责人

交付：

- `BE/src/pvp-v1/map/**`；
- `BE/src/pvp-v1/runtime/**`；
- 29×29 两界斗法台、双方部署区、镜像路径和出生门体积判定；
- 无限阵次、10 核心、经济、人口、真经、遣妖、天劫和胜负；
- 与天兵、神将、羁绊、武器/道具竞技快照的适配层；
- 确定性 smoke。

禁止：在 `pve-v2/runtime.ts` 内增加 PVP 大分支；让对手单位直接互相攻击；客户端决定真经或胜负。

## 3. 房间与匹配负责人

交付：

- `BE/src/pvp-v1/matchmaking/**`；
- `BE/src/pvp-v1/room/**`；
- 排位/休闲队列、MMR 扩圈、10 秒确认、预加载、构筑冻结；
- 自定义房、准备、重连、投降、观战只读投影；
- REST/Socket 路由和速率限制。

验收：未确认不创建对局；陌生人不能加入已锁房；断线和重连边界有自动测试。

## 4. 竞技账户与结算负责人

交付：

- `BE/src/pvp-v1/settlement/**`；
- `BE/src/pvp-v1/rating/**`；
- `BE/src/pvp-v1/history/**`；
- `BE/src/pvp-v1/leaderboard/**`；
- Supabase PVP 独立表、原子结算 RPC、索引、RLS 和 Realtime；
- 赛季、定级、MMR、LP、段位、排行榜、记录和奖励流水；
- Rating Ledger 只追加、账户奖励 Outbox、分块回放 Manifest/Chunk；
- 100 次重放幂等 smoke、并发结算 smoke、榜单重建 smoke。

禁止：复用旧 `best_survived_waves/best_score` 作为段位；把排行榜塞回账户 JSON；信任客户端结果。

结算硬约束：同一事务锁定双方开局冻结的 rating 行并写入互补结果；账户奖励暂时失败只能进入 `reward_pending` 重试，不能回滚或静默丢弃已提交段位。

## 5. 回放与反作弊负责人

交付：

- `BE/src/pvp-v1/replay/**`；
- 双方动作、规则快照、随机袋承诺、检查点哈希；
- 回放保留、举报保全和只读访问；
- 异常动作、串通、早退和重复对手指标。

验收：同版本从头重演哈希一致；不同版本明确拒绝，不使用当前目录猜测旧局。

## 6. 前端负责人

交付：

- 首页 HUMAN/AGENT 改为 PVE/PVP；
- 删除 Agent 指南和玩家侧 Agent 文案；
- `/pvp`、匹配、房间、战场、结算、记录、详情、榜单、档案页面；
- PVP 专用 hooks/types；
- 复用旧房间/榜单/回放视觉，不复用错误数据协议；
- 响应式和真实浏览器流程测试。

验收：前端不预扣真经、核心、段位或奖励；所有数值来自服务端快照/收据。

## 7. 项目经理统一联调门

每个模块合入前必须通过：

1. shared、BE、FE TypeScript 检查；
2. PVE 全量 smoke，证明没有污染 PVE；
3. PVP 地图/阵次/压力/胜负 smoke；
4. 匹配确认、断线重连、投降和无效局 smoke；
5. 结算幂等、并发、段位和榜单 smoke；
6. 前端生产构建；
7. 真实浏览器：首页 → PVP → 匹配/房间 → 游戏 → 结算 → 记录 → 榜单；
8. 数据库迁移可重复执行，回滚策略和旧 competition 数据只读策略明确；
9. `git diff --check`；
10. 完成总设计第 18 节的逐条证据审计。

旧模块额外回归门：动态 PVP 房间必须各自拥有 recorder；客户端自报 `isVictory` 不得产生 PVP 赛果；PVP 重连不得删除玩家战斗状态；公开投影不得泄露对手托盘、备战席、精确资源或未使用道具。
