# AgensTD 深度测试报告（2026-08-28）

## 1. 结论

**整体发布结论：不建议当前版本直接公开发布，PVP 应判定为 No-Go。**

PVE 的真实主链、渲染性能、断线恢复、结算展示与多分辨率适配表现稳定；后端 `release:verify`、前端 smoke、PVP 20 局双浏览器 E2E 也大面积通过。但专项测试确认了多项未被现有门禁捕获的权威性、公平性、持久化和资源生命周期缺陷：客户端可伪造 PVE 通关与排名、密码房不校验密码、PVP 奖励 outbox 无生产消费者、后台标签页会被判掉线败、错峰双断线可把败局变平局、活动 PVP 无法跨进程恢复、load-failed 对局不结算也不回收。

建议将 PVE 限定在内部或 staging 继续验证；PVP 在 P1 问题关闭并补齐真实 Supabase/重启/长时网络门禁前不得公开上线。

## 3. P1：发布阻断缺陷

### P1-01 PVE 密码房完全不校验密码

- 创建房间时密码仅被转成 `hasPassword` 布尔值，房间模型不保存可验证凭据：`BE/src/network/rest-api.ts:510`、`BE/src/core/Room.ts:29`。
- Socket `JOIN_ROOM` 不读取或验证密码：`BE/src/network/socket-gateway.ts:358`。
- 已复现第二个认证身份不带密码直接进入密码房并占据 P2。
- 影响：密码房实际等同公开房，任意认证用户可占位、骚扰或干扰开局。

### P1-02 客户端可伪造 PVE 通关、隐藏关解锁与 Level 5 排名

- `POST /api/replays` 信任客户端提交的 `isVictory` 和 `level`：`BE/src/network/rest-api.ts:667`。
- 进度存储直接据此更新最高解锁关与 Level 5 通关数：`BE/src/data/progress-store.ts:60`。
- 已复现提交 `{"isVictory":true,"level":5}` 后 HTTP 201，并立即得到 `highestUnlockedLevel:6`、`level5ClearCount:1`。
- 数据库写入还是 fire-and-forget；远端写失败时接口仍可能返回 `stored:true`：`BE/src/data/progress-store.ts:74`。
- 影响：排名、解锁和玩家进度可被任意认证客户端作弊，且确认结果可能在重启后丢失。

### P1-03 PVP 活动对局无法跨进程恢复

- 活动比赛与自定义房均只存在进程内 Map：`BE/src/pvp-platform-v1/service.ts:139`。
- 新实例不恢复活动比赛：`BE/src/pvp-platform-v1/service.ts:148`、`:555`。
- 已复现共享同一 Store 的实例 B 无法查询实例 A 已启动的 match，返回 `MATCH_NOT_FOUND`。
- 影响：部署、崩溃或迁移会直接丢失进行中对局，无法继续、断线恢复或权威判定 no-contest。

### P1-04 load-failed 使 PVP 对局永不结算且永不回收

- failed load ACK 将 runtime 置为 `voided`：`BE/src/pvp-v1/runtime.ts:255`。
- `voided` 又被视为 quiescent：`BE/src/pvp-v1/runtime.ts:415`。
- ACK 路径不结算，后续 tick 跳过该 runtime，reaper 又只回收有 `settledDetail` 的对局：`BE/src/pvp-platform-v1/service.ts:274`、`:469`、`:653`。
- 已复现推进 5 tick 后仍为 `voided`、无 stored detail，live match/custom room 均保留。
- 影响：缺少 no-contest 审计；可通过反复建房并 load-fail 持续放大内存占用。

### P1-05 PVP 奖励 outbox 没有生产消费者

- 结算会创建 `pending` 奖励事件：`BE/src/rank-v1/service.ts:208`。
- Store 虽提供 claim/complete/fail，但全仓调用只存在于实现和 smoke，生产流程没有 worker。
- 奖励包含 honor/gold：`BE/src/pvp-platform-v1/service.ts:673`。
- 影响：玩家完成 PVP 后排名可能结算，但 honor/gold 永久 pending、不会真正进入账户。

### P1-06 错峰双断线可把先断线者的确定败局变成平局

- 当两人都断线时，runtime 要等两人都超时才结算 `simultaneous_draw`：`BE/src/pvp-v1/runtime.ts:905`。
- 已用短阈值复现：A 在 tick 0 断线、B 在 tick 2 断线；A 到期时仍保持 playing，最终等 B 到期后判平局。
- 影响：玩家可在对手即将因断线判负时主动断线，将胜负改写成平局。

### P1-07 后台标签页超过断线宽限会被误判败北

- 前端页面隐藏时主动中止 SSE：`FE/hooks/use-pvp-data.ts:459`。
- 服务端把最后一个 SSE 连接关闭直接标记为断线：`BE/src/pvp-platform-v1/service.ts:281`。
- 短阈值联调已复现隐藏/取消订阅后直接触发 `disconnect_forfeit`；现有 E2E 仅覆盖 1.2 秒后台，没有越过生产 60 秒宽限。
- 影响：玩家切后台看消息或处理系统弹窗超过 60 秒会无故输掉比赛。

### P1-08 同一玩家可同时启动多场自定义 PVP

- 排位队列有 active-match 保护，但自定义房 create/join/ready 路径没有：`BE/src/pvp-platform-v1/service.ts:409`。
- 已复现同一 Alice/Bob 在两个房间同时 ready，生成两个同时 loading 的 live match。
- 影响：会话、结算、断线与奖励归属出现冲突，并放大资源消耗。

### P1-09 自定义房缺少幂等、限流、账号配额和空房 TTL

- REST 创建房间不消费 requestId，也没有 limiter：`BE/src/network/pvp-rest-api.ts:56`、`:234`。
- 已复现同一 token、同一 requestId 连续 20 次创建房间，20 次均返回 201 并生成唯一房间。
- reaper 只回收已结算 match 关联房，空房不按设计中的 10 分钟 TTL 回收：`BE/src/pvp-platform-v1/service.ts:653`。
- 影响：正常重试会重复建房；认证用户可以制造房间/收据/同步哈希的内存与 CPU 放大。

### P1-10 PVP 双方征兵共用全局 PRNG

- runtime 只有一个全局 PRNG：`BE/src/pvp-v1/runtime.ts:161`。
- 已复现相同 seed 下，Alice 多征一次会改变 Bob 下一次征兵结果。
- 影响：一方动作到达顺序会改变另一方随机结果，不满足按 side + bagIndex 隔离的公平随机袋设计。
- 这是设计文档中尚未完成的能力，但在公开竞技发布前仍属于阻断项。

### P1-11 前端 CI 因图片预算脚本误报而稳定失败

- `cd FE && pnpm test:ci` 在 build 成功后报 `referenced image is missing from dist: art/equipment/${s}.webp`。
- `FE/scripts/check-build-budget.mjs:97` 扫描压缩 JS 时把动态模板变量当作实际文件名；真实图片目录存在。
- 影响：每次前端 CI 都失败，串行的后续 smoke 被跳过，发布门禁不可用。

## 4. P2：高优先级缺陷

### P2-01 README 指定的一键启动命令不可用

- 复现：仓库根目录执行 `./dev-stack.sh start`。
- 实际：后端立即退出，日志为 `zsh:1: command not found: SUPABASE_URL=`。
- 根因：默认命令以变量赋值开头（`dev-stack.sh:19`），启动器却拼接成 `exec ${start_command}`（`:221`）；zsh 将 `SUPABASE_URL=` 当作命令。
- 影响：README 的本地/局域网一键联调入口失效。使用 `env SUPABASE_URL= ... pnpm dev` 可临时绕过。

### P2-02 PVP SSE 在校验 match/参与者前发送 200 headers

- `BE/src/network/pvp-rest-api.ts:105` 先 `flushHeaders()`，再调用可能抛出 403/404 的订阅逻辑。
- 已复现陌生人访问存在的 match、参与者访问不存在的 match 时服务端记录 `Cannot set headers after they are sent`，客户端只得到连接终止而不是结构化错误。
- 影响：错误恢复协议被破坏，并可造成日志放大。

### P2-03 匹配与命令收据缺少淘汰策略

- `acceptedMatches`、tickets、request receipts 不淘汰：`BE/src/matchmaking-v1/service.ts:84`。
- 已复现完成 100 场后 `acceptedMatches=100`；后续查询还会线性扫描。
- PVP runtime 的 `commandReceipts` 也会按唯一 requestId 无界增长：`BE/src/pvp-v1/runtime.ts:130`、`:1079`。
- 影响：长时间运行后内存与查询延迟持续上升。

### P2-04 服务配置缺少有效边界校验

- `BE/src/config/server-config.ts:42` 接受任意有限数值，多数 port/tick/map/rate-limit/replay 配置没有正数、整数或合理上限校验。
- 影响：错误环境变量可能导致晚期启动失败、异常 tick 速率、动作全部拒绝或容量异常。

### P2-05 优雅关机不保存最终 PVE checkpoint

- coordinator shutdown 仅取消订阅并清空 context：`BE/src/pve-checkpoint-v1/coordinator.ts:161`。
- server shutdown 只等待 replay flush：`BE/src/server.ts:249`。
- 影响：正常滚动发布也可能回退至上个周期 checkpoint；默认 50 ticks，约 5 秒自主战斗状态可能倒退。

### P2-06 移动端 11 个导航入口丢失可访问名称

- 390px 下首页 3 个局外入口、局外系统 3 个链接、PVP 5 个导航链接在可访问性树中均为空名。
- 移动 CSS 隐藏唯一文本节点，图标又无替代名：`FE/app/globals.css:899`、`:4828`。
- 影响：手机屏幕阅读器无法区分导航目的地。

### P2-07 PVE/PVP 模态框缺少焦点管理和 dialog 语义

- PVP 创建房间、投降确认以及 PVE 创建房间均没有 `role="dialog"`、`aria-modal`、初始焦点、焦点圈定和 Escape 关闭：`FE/pages/pvp-page.tsx:242`、`:321`，`FE/pages/tower-defense-frontend-page.tsx:338`。
- 实测弹窗打开后焦点仍停在背景按钮，继续 Tab 会进入背景控件。
- 影响：键盘用户可误操作背景，读屏不会正确宣布弹窗；投降确认风险更高。

### P2-08 嵌套交互控件造成键盘/读屏行为错误

- 主页模式卡使用 `article role="button"`，内部又放原生 CTA button：`FE/pages/tower-defense-frontend-page.tsx:461`、`:486`。键盘产生两个触发同一动作的焦点，读屏把整张卡和 CTA 分别宣布为按钮。
- 武器槽外层 button 内嵌 `i role="button"`：`FE/pages/meta-system-page.tsx:305`。移除控件无可访问名称，也没有 Enter/Space 处理。
- 影响：键盘导航重复或不可操作，交互语义无效。

## 5. P3 与体验风险

- PVP 房间刷新、创建房间关闭等图标按钮没有 `aria-label`：`FE/pages/pvp-page.tsx:239`、`:242`。
- 多处异步错误不是 alert/live region，读屏不会主动播报：`FE/pages/pvp-page.tsx:102`、`FE/pages/meta-system-page.tsx:103`、`FE/pages/gaming-page.tsx:2086`。
- 390px 登录页的装饰性 boot log 使用 `whitespace-pre`，同时页面 `overflow-hidden`，右侧内容被明显裁切：`FE/pages/login-page.tsx:23`、`:70`。
- Phaser gzip 为 392,586/409,600 bytes，预算已使用约 95.8%，只剩约 16.6KiB。
- `/arsenal` 在 390px 下一次性渲染完整武器目录，页面高度约 17,791px；低端移动设备有长列表布局与滚动风险。

## 6. 数值与门禁风险

- 快速 balance smoke 的 easy L1、easy L10、normal L10、hard L1 都是 512/512、100% 通关，经济行为也高度一致；它不足以证明难度梯度。
- 真正带目标通关率的 `pnpm test:balance:full` 运行约 7 分钟仍无中间进度，本轮为及时收束而中断，不能视为通过。
- `release:verify` 只执行快速 `test:balance`，未纳入 `test:balance:full`。
- 当前 PVE 实机主链在自动构筑下第 16 波败北，说明真实玩法并非快速模型所显示的全难度 100% 通关；应统一数值门禁与真实构筑模型。

## 7. 覆盖盲区

- Supabase migration 仅做静态 SQL 检查，`actualDatabaseApplyVerified:false`；未验证真实 migration、RLS、RPC、schema drift、双人并发结算与故障切换。
- auth smoke 使用 fake verifier；未覆盖真实 JWT 过期、issuer/audience、密钥轮换与 JWKS。
- 未覆盖真实公网 NAT、代理 SSE timeout/乱序、实体触控设备与 WebKit。
- 未完成完整 PVP 数值 Monte Carlo、阵容支配率、正式随机袋、构筑冻结、回放及奖励 outbox 到玩家账户的 E2E。
- 未验证 SIGTERM 前最终 PVE checkpoint 与恢复哈希一致性。
- `test:balance:full` 本轮未完成。

## 8. 建议修复顺序与复验门槛

1. 立即下线或封禁 legacy `POST /api/replays` 的进度写入；所有通关、解锁、排行必须绑定服务端权威 match/settlement。
2. 修复 PVP 奖励消费者、void 结算/reaper、活动比赛 checkpoint/recovery。
3. 修复后台页连接语义与错峰双断线裁决，并新增超过 60 秒的真实长时 E2E。
4. 增加 PVP 全局 active-match 约束、房间幂等/限流/配额/TTL、收据淘汰。
5. 实现双方独立随机袋；补充确定性重放和不同动作顺序下的公平性测试。
6. 修复密码房协议与安全存储，不在客户端或日志中泄露原密码。
7. 修复前端 CI 误报和 `dev-stack.sh`，恢复可信、可复跑的发布门禁。
8. 修复移动端可访问名称、dialog 焦点圈定和嵌套交互控件。
9. 将真实 Supabase staging、进程重启、outbox 入账、全量数值模型纳入发布硬门。

最低复验要求：所有 P1 自动化复现转绿；`release:verify`、前端 `test:ci`、PVE experience、PVP 20 局 E2E 全绿；追加 60 秒后台/错峰断线、PVP 重启恢复、load-failed no-contest、奖励到账、密码房、伪造 replay 拒绝、房间 TTL/限流、真实 Supabase migration/RLS/RPC 测试。
