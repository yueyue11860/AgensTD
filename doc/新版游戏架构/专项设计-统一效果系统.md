# 专项设计：统一效果系统

> 状态：V0.1 架构草案
>
> 目标：让神将、羁绊、武器、道具、敌人和关卡修正使用同一套可执行、可验证、可回放的效果语言。

## 一、设计原则

1. 配置只描述规则，运行时统一执行，不为单个神将硬编码战斗流程。
2. 所有效果必须结构化，不解析 `"crit_25%"` 之类字符串。
3. 所有效果必须能说明来源、目标、持续时间、叠加组和上限。
4. 所有随机判定由服务端种子随机数生成，并写入回放事件。
5. 属性展示值与服务端结算值来自同一计算结果。
6. 新效果类型必须注册、校验并配套最小测试，不能只在配置里创造新字符串。

## 二、统一效果模型

每个效果定义包含以下标准字段：

```json
{
  "effectId": "tangsanzang_mantra_vulnerable",
  "type": "status_apply",
  "source": {
    "kind": "skill",
    "sourceId": "jinguzhou_mantra"
  },
  "target": {
    "scope": "enemies_in_radius",
    "radius": 2,
    "filters": ["alive"]
  },
  "chance": 1,
  "payload": {
    "statusId": "vulnerable_all",
    "magnitude": 0.2
  },
  "durationMs": 6000,
  "stacking": {
    "stackGroup": "vulnerable_all",
    "policy": "strongest_refresh",
    "maxStacks": 1
  },
  "tags": ["control", "soft_control", "vulnerable"]
}
```

运行时实例在定义之外增加：`instanceId`、`sourceEntityId`、`ownerPlayerId`、`targetEntityId`、`startedAtTick`、`expiresAtTick`、`remainingStacks` 和随机判定结果。

`source.kind` 首版固定为：`skill`、`passive`、`synergy`、`weapon`、`active_item`、`passive_item`、`enemy`、`stage_rule`。每个修改器必须同时保留 `sourceId`；武器和道具效果还要保留槽位快照版本，便于重连、回放和属性来源展开。

## 三、首批效果类型注册表

| 效果类型 | 用途 | 必需参数 |
| --- | --- | --- |
| `damage` | 直接或多段伤害 | damageType、系数/固定值、是否暴击 |
| `damage_over_time` | 灼烧、中毒、雷区 | damageType、周期、持续时间、叠加规则 |
| `stat_modifier` | 攻击、攻速、范围、暴击、冷却等 | stat、operation、value |
| `conditional_stat_modifier` | 对 Boss、受控目标等条件增伤 | condition、stat、operation、value |
| `status_apply` | 减速、眩晕、定身、封禁、易损、破甲 | statusId、magnitude、duration |
| `path_displacement` | 击退、拉拽 | direction、distance、Boss 系数 |
| `summon_unit` | 召唤物 | unitId、数量、持续时间、上限、生成规则 |
| `spawn_zone` | 雷区、水域、八卦炉等持续区域 | shape、duration、tickEffects |
| `cooldown_modify` | 固定或比例减 CD | targetSkill、operation、value、触发上限 |
| `resource_modify` | 局内斋饭等玩家级临时资源 | resource、operation、value、归属 |
| `attribute_copy` | 召唤物继承主人属性 | source、statMap、ratio |
| `effect_parameter_patch` | 羁绊/专武修改已有技能参数 | targetEffectId、parameter、operation、value |

不设置万能脚本型 `custom` 效果。确需新增能力时，先增加一个有明确语义和测试契约的新类型。

改字、刷新召唤托盘等会改变权威状态结构的行为，不伪装成战斗效果，进入“规则动作注册表”。首批动作包括 `replace_character_token`、`refresh_summon_tray` 和 `grant_general_experience`；动作同样要求服务端校验、幂等、事件记录与回放支持。新版没有扩地动作。

## 四、属性计算顺序

统一使用以下流水线：

1. 神将静态基础值；
2. 等级成长；
3. 武器基础属性；
4. 羁绊常驻修改；
5. 神将被动与常驻光环；
6. 被动道具常驻修正；
7. 关卡常驻修正；
8. 主动道具与其他战斗临时状态；
9. 敌方施加的易损、破甲与抗性；
10. 最终全局上限/下限钳制。

每一层只生成带来源的修改器，不直接覆盖上一层结果。UI 属性详情可以按来源展开，便于玩家理解和开发排错。

## 五、操作与叠加规则

### 1. 属性操作

- `add_flat`：固定值相加；
- `add_ratio`：同层百分比先相加；
- `multiply`：独立乘区；
- `override`：明确覆盖，仅用于形态切换；
- `min` / `max`：钳制型规则。

推荐公式：`最终值 = ((基础值 + 固定值) × (1 + 同层比例和) × 独立乘区) + 最终固定值`，之后执行全局上下限。

### 2. 状态叠加策略

- `refresh`：不增加层数，只刷新持续时间；
- `extend`：延长持续时间，但有最大时长；
- `stack`：增加层数，受 `maxStacks` 限制；
- `strongest_refresh`：仅保留最强幅度并刷新时间；
- `replace`：新效果替换旧效果；
- `independent`：每个来源独立计时，仅限明确允许的持续伤害。

所有效果必须声明 `stackGroup`。同组如何叠加由状态定义决定，不由释放者临时决定。

## 六、控制系统专项规则

### 1. 三类控制

- 软控：减速、易损、破甲、控制抗性削减；
- 硬控：眩晕、定身、封禁；
- 路径位移：击退、拉拽。

### 2. 减速

- 同一目标只生效幅度最强的减速，其他来源保留计时但不叠乘；
- 普通怪最低移动速度为基础速度的 20%；
- Boss 最低移动速度为基础速度的 50%；
- 免疫不等于删除效果，UI 应显示“抵抗”或折算后的真实幅度。

### 3. 硬控递减

同一目标在最近 8 秒内连续受到硬控时，持续时间依次乘以：`1.0 → 0.65 → 0.4 → 0.2`。8 秒未再受硬控则恢复。

- 普通怪单次硬控上限：4 秒；
- 精英单次硬控上限：2.5 秒；
- Boss 单次硬控上限：1.5 秒；
- 控制穿透只抵消控制抗性，不能突破单次上限或递减层级。

### 4. 路径位移

- 敌人位置以 `pathProgress` 为权威值；
- 击退减少路径进度，拉拽向指定路径进度靠拢；
- 不直接把二维坐标写到任意位置；
- 普通怪单次最大位移 2 格、Boss 最大 0.5 格；
- 不允许被击退到生成点之前，也不允许跨越不相连的路径段。

### 5. 易损与破甲

- 全伤易损普通怪上限 +60%，Boss 上限 +35%；
- 单一伤害类型易损可使用独立组，但最终仍受总增伤预算限制；
- 破甲先修改护甲，再进入伤害公式；护甲最低值默认 0，除非关卡规则明确允许负甲。

## 七、冷却与攻速边界

- 常驻冷却缩减上限：40%；
- 最终技能冷却不得低于 1 秒；
- “击杀减 CD”必须配置单次触发值与每次释放周期内的触发上限；
- 攻速采用每秒攻击次数，最终上限先定为 5 次/秒，特殊持续技能另走 Tick 伤害；
- 单次攻击的投射物、弹射和召唤数量均要纳入效果预算，避免全屏高攻速导致性能雪崩。

## 八、召唤物继承

召唤物保存“基础模板 + 主人引用 + 继承比例”，不复制一份永久静态属性。

- 主人升级、羁绊启用或武器变化后，存活召唤物同步更新；
- 召唤物只继承配置白名单内的属性；
- 默认继承攻击、攻速、暴击和指定增伤，不自动继承攻击范围、主动技能与再次召唤能力；
- 使用 `modifierVersion` 缓存有效属性，只在相关来源变化时重算，不每 Tick 全量重算。

### 逻辑神将与多格汉字表现

神将不是独立单格棋子，而是引用 2～4 个汉字 Token 的逻辑聚合体。统一效果系统只面向 `generalId + ownerPlayerId` 的逻辑施法者，不要求创建角色模型。

- 普攻和技能原点使用全部组成格的几何中心；
- 固定整体迁移不创建新施法者，也不重置效果、经验或 CD；
- 字符序列被破坏后，神将进入失活状态，被动、光环和羁绊修改器立即移除；
- `cooldownRemainingMs` 继续按对局时间递减，重新组合后不重置；
- 是否保留已生成的持续区域或召唤物，由对应效果定义的 `sourceInactivePolicy` 决定，默认持续区域自然结束、依赖本体的召唤物退场。

### 武器与道具来源生命周期

- 武器与道具均从开局不可变快照读取，局外中途换装不影响当前对局；
- 武器来源随对应神将激活而挂载、失活而移除，重新组合只恢复原效果，不重复触发“首次生效”；
- 被动道具在玩家对局状态初始化后挂载，到结算结束统一移除；
- 主动道具只在服务端确认使用成功后创建效果实例或执行规则动作；
- 同一来源的重复请求必须通过 `requestId` 幂等，不能叠出第二份效果或重复消耗次数。

## 九、控制与增益贡献记录

每个敌人维护短期贡献账本：

```text
ownerPlayerId + sourceGeneralId → damage、hardControlMs、slowEquivalentMs、vulnerableAmplifiedDamage、supportAmplifiedDamage、lastContributedAt
```

敌人死亡时，先以最后有效伤害确定击杀玩家，再只读取该玩家最近 5 秒的合格记录；物理、魔法、召唤、控制资格权重分别为 3、3、3、1。每只普通小怪的 1000 点经验按权重整数分配，余数使用最大余数法。无实际影响的溢出控制、对已达减速下限目标继续减速不计贡献；击杀玩家没有合格神将时经验自然损失，不转给其他玩家。基础事件契约见《专项设计-基础战斗事件与直接攻击.md》。

## 十、专项验收标准

1. 任意效果都能从配置校验失败中得到明确字段错误。
2. 相同输入、相同种子、相同操作序列得到完全一致的战斗结果。
3. UI 展示的最终属性能展开到每个来源。
4. 效果移除后不会污染基础属性或留下幽灵加成。
5. 控制链、冷却缩减和攻速无法突破全局上限。
6. 至少覆盖伤害、减速、眩晕、易损、击退、召唤、光环、减 CD 的单元与组合测试。
7. 以 100 个敌人、30 个防守单位和 20 个召唤物为压力基线完成性能测试。
8. 武器、主动道具、被动道具均能按来源展开，并在拆将、重组、断线重连和结算时正确挂载或移除。
9. 改字和托盘刷新等规则动作可被服务端校验并由回放完整复现，扩地动作不在注册表中。
