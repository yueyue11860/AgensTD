# 征兵与棋盘交互架构

> 状态：V0.1 PVE 首版规则
>
> 范围：大本营随机池、召唤托盘、棋盘、人口、汉字神将组合、固定/解除固定、拆合后成长保留。

## 一、核心原则

1. 大本营是服务端内部随机池，玩家不可见、不可直接选择。
2. 玩家只操作 5 格召唤托盘和己方棋盘。
3. 点击召唤会强制刷新整个托盘，不要求旧单位已经用完。
4. 神将第一版保持纯汉字表现，不融合成单格角色模型。
5. 棋盘空间与人口是两套限制：汉字消耗空间但不消耗人口，激活神将消耗人口但继续占据多个汉字格。
6. 神将成长绑定玩家与神将 ID，不绑定某次字符排列。
7. 所有随机、资源扣除和拖拽结果以服务端判定为准。
8. 不存在扩地操作；全部可部署格开局开放，阵容规模只受人口上限约束。

## 二、区域与状态

### 1. 大本营

大本营只保存生成召唤结果所需的权威数据：

- `remainingCharacterTokens`：本局尚未抽出的有限神将字符 Token；
- `soldierRollTable`：可重复生成的小兵类型和权重；
- `characterRollChance`：当前仍有字符时，每个召唤位生成字符的统一概率，首版固定为 1000 基点（10%）；
- `rngState`：对局种子随机数状态；
- `recruitCostRule`：本次召唤所需斋饭；
- `recruitSequence`：已经完成的召唤批次编号。

大本营是一个统一生成池。有限字符与可持续天兵共用同一个抽取入口，但生命周期不同：字符 Token 只能抽出一次，天兵可以重复生成。实现上允许分别保存供应状态和概率表，但不得向玩家表现为两个池或两次抽取。

### 2. 召唤托盘

每位玩家固定拥有 5 个托盘槽，每格状态为：

```text
empty | soldier(unitId) | character(tokenId, glyph)
```

召唤托盘内单位不参与战斗、不占人口、不形成神将和羁绊。托盘只承担待部署、临时收纳和棋盘换位功能。

### 3. 棋盘

棋盘格至少区分：

```text
path | deployable_empty | occupied | blocked
```

可部署单位：

- 小兵棋子：1 格、1 人口；
- 汉字棋子：1 格、0 人口；
- 临时召唤物：由技能系统管理，不作为普通可拖拽棋子。

神将不是额外棋子，而是覆盖若干汉字棋子的逻辑聚合状态。

## 三、召唤批次

### 1. 玩家操作

玩家点击「召唤」后：

1. 客户端发送 `RECRUIT_BATCH`；
2. 服务端校验对局状态、玩家斋饭和 0.5 秒召唤操作锁；
3. 服务端扣除本批次斋饭；
4. 当前托盘中未部署的 5 格内容全部进入弃置区；
5. 服务端按顺序生成 5 个新结果；
6. 客户端播放约 0.5 秒固定征兵动画；
7. 动画完成后一次揭示全部结果并解除召唤按钮锁。

随机结果在服务端收到合法操作时就已经确定，客户端动画不参与随机判定。断线重连时直接恢复权威托盘结果。

初始斋饭为 10。第 `n` 次成功征兵费用为 `5 + 2 × (n - 1)`，即 5、7、9、11……。余额不足或请求失败时，不扣斋饭、不推进批次编号、不改变托盘。

### 2. 单格生成算法

```text
若 remainingCharacterTokens 非空
  按 characterRollChance 判定字符/小兵
  若为字符：从剩余字符 Token 中按配置权重抽取并永久移出大本营
  若为小兵：从 soldierRollTable 抽取，可重复
否则
  必定从 soldierRollTable 抽取小兵
```

五个槽依次生成，每次字符抽取都会立刻更新剩余 Token，保证同一 Token 不会在同一批次重复出现。

- 进入字符分支后，所有剩余字符 Token 等权，不按神将品质和玩家当前缺字加权。
- 同字存在多张 Token 时，每张 Token 仍各自等权，因此该字的总出现机会随剩余 Token 数自然变化。
- 进入天兵分支后，首版刀、枪、弓、骑等权，各占该分支的 25%。
- 第一版不提供连续未出字符的系统保底；后续保底机制由道具专项定义。
- 第一批征兵必须至少包含 1 个天兵。若五个正常结果全部是字符，则把最后抽出的字符 Token 原样放回剩余池，并将该槽按天兵概率表重抽。该例外仍写入回放。

### 3. 强制刷新

再次召唤不检查托盘是否为空。旧内容的处理规则：

- 小兵：直接弃置；
- 神将字符：进入弃置区，不返回大本营，因此可能永久错过对应神将；
- 后续改字、找回、垃圾桶等能力是否操作弃置区，由道具专项单独定义。

## 四、托盘与棋盘拖拽

### 1. 单格交换矩阵

| 来源 | 目标 | 结果 |
| --- | --- | --- |
| 托盘有单位 | 棋盘空格 | `1→0`，单位部署到棋盘，托盘变空 |
| 托盘空格 | 棋盘有单格棋子 | `0←1`，棋子撤回托盘，棋盘变空 |
| 托盘有单位 | 棋盘有单格棋子 | `1↔1`，两者原子互换 |
| 托盘空格 | 棋盘空格 | `0→0`，拒绝，无状态变化 |

同一矩阵反向拖拽结果一致。服务端把交换作为一个原子操作执行，不能先清空来源、再因目标校验失败而丢失棋子。

### 2. 棋盘内移动

- 单格小兵、未固定汉字可以移动到另一个空部署格；
- 第一版不直接交换两个棋盘占用格，玩家需要使用空格或召唤托盘中转；
- 路径、阻挡格和越界格不可作为目标；
- 移动完成后统一重新识别受影响区域的神将组合与人口变化。

### 3. 人口校验

- 小兵从托盘部署到棋盘时，需要至少 1 个剩余人口；
- 单个汉字部署不校验人口；
- 最后一个字符落位并形成新神将时，需要至少 1 个剩余人口；
- 若形成神将会超过人口上限，本次移动整体拒绝并恢复原状态；
- 破坏神将字符序列时立即释放该神将的 1 点人口。

### 4. 天兵合成

- 两个同类型、同等级且低于 5 级的天兵可合成为高一级天兵；
- 支持棋盘/托盘之间的四种位置组合，升级结果保留在目标位置；
- 两个棋盘天兵合成后人口从 2 降为 1；
- 合成、位置变化、人口变化和攻击计时器重置必须是同一个服务端原子事务；
- 详细规则见《小兵体系架构.md》。

## 五、汉字神将识别

### 1. 首版组合规则

- 只识别棋盘部署区；召唤托盘中的相邻字符不形成神将；
- 只识别同一行、横向连续、从左到右与配方完全一致的字符；
- 中间不能有空格、小兵或其他字符；
- 一个字符 Token 同一时刻只能属于一个激活神将组合；
- 若未来出现重叠配方，按“字符数更多优先，其次配置优先级，最后 `generalId`”确定唯一结果。

示例：

```text
[杨][戬]                 → 激活杨戬，占2格、1人口
[孙][悟][空]             → 激活孙悟空，占3格、1人口
[玉][皇][大][帝]         → 激活玉皇大帝，占4格、1人口
[悟][孙][空] 或中间有空格 → 不激活
```

### 2. 逻辑聚合状态

```ts
interface GeneralFormationState {
  formationId: string
  ownerPlayerId: string
  generalId: string
  characterTokenIds: string[]
  cells: Array<{ x: number; y: number }>
  anchor: { x: number; y: number }
  fixed: boolean
  active: boolean
}
```

`anchor` 使用全部占地格中心点。普攻距离、以自身为中心的技能和表现特效都从该锚点计算。

### 3. 唯一性

`generalProgressById` 是每位玩家的神将权威索引。当前字符数量天然限制首次组合次数，但不能替代运行时唯一性校验。

- 首次形成配方：创建进度记录并触发首次召唤事件；
- 拆开后重新形成：复用原进度记录，不再次触发首次召唤奖励；
- 若未来道具制造出第二套相同配方：第二套字符不能同时激活为同名神将。

## 六、固定、迁移与解除组合

### 1. 状态卡

点击激活神将占地内任意字符，打开同一张神将状态卡，显示：

- 神将名称、品质、流派和阵营；
- 当前等级与经验；
- 攻击、攻速、范围与技能 CD；
- 武器与羁绊；其中武器只展示开局配置快照，局内不能佩戴、卸下或切换；
- 当前固定状态；
- 「固定」或「解除固定」按钮。

### 2. 固定

- 固定后，整组字符成为一个拖拽选择单元；
- 第一版只允许在棋盘内横向整体迁移；
- 目标位置必须存在相同长度的连续空部署格；
- 整体迁移不改变经验、等级、CD、羁绊或临时状态；
- 固定神将不能直接与单个托盘格交换。

### 3. 解除固定

- 解除固定只解除拖拽锁，不立即让神将失活；
- 字符仍连续且顺序正确时，神将继续攻击和释放技能；
- 任一字符被移走导致序列不成立时，逻辑聚合失活、人口释放、羁绊重新计算；
- 重新排列正确后，恢复同一神将进度。

## 七、成长与拆合防利用

每位玩家按 `generalId` 保存：

```ts
interface GeneralProgressState {
  generalId: string
  firstActivatedAtTick: number
  experience: number
  level: number
  cooldownRemainingMs: number
  hasTriggeredFirstActivationReward: boolean
}
```

拆开神将时：

- 经验和等级保留；
- 技能 CD 继续随对局时间正常流逝，不重置、不暂停；
- 被动、光环和羁绊立即失效；
- 由该神将产生的持续区域按原持续时间结束；
- 依赖神将持续存在的召唤物立即退场，具体由效果定义声明；
- 重新组合不能重复触发首次召唤奖励和首次掉落。

## 八、服务端动作建议

```ts
type BoardAction =
  | { action: 'RECRUIT_BATCH' }
  | { action: 'SWAP_TRAY_BOARD'; trayIndex: number; boardCell: Position }
  | { action: 'MOVE_BOARD_PIECE'; from: Position; to: Position }
  | { action: 'MERGE_SOLDIERS'; sourceEntityId: string; targetEntityId: string }
  | { action: 'SET_GENERAL_FIXED'; formationId: string; fixed: boolean }
  | { action: 'MOVE_FIXED_GENERAL'; formationId: string; targetStart: Position }
```

所有动作都应携带 `actionId`、`clientKnownTick` 和受影响区域的预期修订号，服务端返回接受/拒绝原因及权威 Tick。客户端只做预测动画，不自行决定人口、组合、经验或随机结果。完整协议见《专项设计-MatchStateV2与前后端协议.md》。

## 九、首版暂不处理

- 纵向、折线或任意方向姓名组合；
- 固定神将整体进入召唤托盘；
- 棋盘两个占用格直接互换；
- 神将融合为单格角色模型；
- 多套同名神将同时激活；
- PVP 的双方交互、真经和无限波次；
- 改字、找回、垃圾桶等道具对弃置区的操作；
- 武器碎片的跨局结算（由武器系统专项和结算服务处理）。

## 十、最小验收用例

1. 召唤扣除斋饭并在 0.5 秒操作锁后展示 5 个确定结果。
2. 连续点击不能绕过召唤锁或重复扣费。
3. 强制刷新会弃置旧托盘内容，有限字符不会回池。
4. 三类有效托盘/棋盘交换均保持单位总数，`0→0` 无副作用。
5. 人口 10/10 时允许部署汉字，但拒绝会形成第 11 个战斗单位的最后一步。
6. `[孙][悟][空]` 正确激活，错误顺序、空格和跨行均不激活。
7. 固定神将可整体迁移，迁移前后经验、CD和羁绊不变。
8. 解除固定后移走一个字符，神将失活并释放人口；重新组合恢复经验和剩余 CD。
9. 同一字符不能同时属于两个逻辑神将。
10. 断线重连后托盘、棋盘、固定状态、人口、字符 Token 和神将进度完全一致。
11. 前三次成功征兵分别花费 5、7、9 斋饭，余额不足的失败请求没有副作用。
12. 两个同类同级天兵合成成功；类型不同、等级不同和 5 级合成都被拒绝。
13. 任意普通召唤槽的字符分支概率为 10%，字符 Token 等权；第一批在极端全字符结果下会回退一张 Token 并保证至少一个天兵。
