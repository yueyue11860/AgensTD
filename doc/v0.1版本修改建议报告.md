# AgensTD v0.1 版本修改建议报告

编制日期：2026-08-28  
依据：两轮深度测试、真实 Chromium 功能联调、PVE/PVP 权威性测试、前后端 smoke 与压力测试  
目标读者：开发 Agent、前端 Agent、后端 Agent、QA Agent  
版本目标：将当前版本从“可演示/可联调”提升到“可控范围内稳定发布”

## 0. 执行摘要

当前版本不满足公开发布条件，主要原因不是基础页面不可用，而是：

1. 41 件武器中 22 件是可展示、可合成、可装备但战斗效果完全未接线的空壳；另有 3 件仅部分生效。
2. PVE 首次教学不暂停战斗，玩家可能还未完成召唤、部署或道具操作就失败。
3. PVP 存在奖励不入账、load-failed 不结算、活动对局不跨进程恢复、断线裁决可被改写、后台页面误判败北等问题。
4. legacy replay 接口信任客户端通关结果，可伪造 PVE 解锁和排行榜。
5. 密码房不校验密码，房间接口缺少幂等、限流、配额和 TTL。
6. 前端发布门禁存在稳定误报，一键启动脚本不可用；可访问性和移动端弹窗仍有明显缺陷。

本报告按“必须先修复 → 可发布前修复 → 发布后优化”排列。开发 Agent 应按任务编号实施，并在每项完成后满足对应验收标准。**不得通过隐藏报错、修改测试数据或关闭校验来使测试变绿。**

## 1. v0.1 放行门槛

以下条件全部满足，才允许将 v0.1 标记为可发布候选：

- P0/P1 任务全部完成并有自动化回归；
- `cd BE && pnpm release:verify` 全绿；
- `cd FE && pnpm test:ci` 全绿；
- PVE 真实体验链路可完成：登录 → 建房 → 选关 → 招募 → 部署 → 使用至少一个主动道具 → 战斗 → 结算；
- PVP 20 局双端 E2E 全绿，并额外通过 60 秒后台、错峰断线、进程重启、load-failed、奖励到账测试；
- 真实 staging Supabase migration、RLS、RPC、重启恢复和 outbox 入账通过；
- 武器不再出现“玩家能装备但战斗静默不生效”的情况；
- 未完成或未接线的内容必须从玩家 API/UI 隐藏，不能继续以正式可获得内容暴露；
- 测试报告中的所有“未验证”项要么补齐真实验证，要么明确降级为不可用并在 UI 标注。

## 2. 实施顺序

### 阶段 A：安全、公平与数据正确性（最高优先级）

先处理 PVE 伪造通关、密码房、PVP 结算/奖励/断线/恢复。这些问题会导致玩家资产、排名和对局结果错误，不能与功能美化并行延期。

### 阶段 B：武器、道具和新手主链完整性

处理武器空壳、部分效果、主动道具未验证、首次教学失败和构筑状态丢失。

### 阶段 C：发布工程与前端交互质量

处理 CI 误报、一键启动、弹窗焦点、移动端无障碍、收据/缓存淘汰和配置边界。

### 阶段 D：数值与真实环境门禁

补齐全量数值、Supabase staging、重启恢复、长时网络、触控/WebKit 等发布前验证。

## 3. P0/P1 必须修复项

### P0-01：关闭或重构 legacy replay 通关写入

问题：`POST /api/replays` 信任客户端提交的 `isVictory`、`level`，可伪造解锁和 Level 5 排名；数据库写入失败时还可能返回成功。

实施要求：

- 立即禁止 legacy replay 接口修改玩家进度、解锁和排行榜；过渡期只能写入隔离的审计表；
- 新进度写入必须绑定服务端生成的 `matchId`、结算记录、规则版本、玩家身份和服务器签名；
- 只允许服务端 `victory` 结算事件更新 `clearsByStageKey`、解锁和排行；客户端上传的 `isVictory`、`level` 只能作为非权威展示字段；
- 持久化失败时接口返回明确失败，不得返回 `stored:true`；
- 对旧接口增加弃用响应和监控指标。

验收标准：

- 伪造 `isVictory:true, level:5` 返回 4xx，进度、排行和解锁均不变化；
- 无对应服务端结算的 replay 永远不能写入通关；
- Supabase 写失败时客户端收到失败且不会产生“已入账”假象；
- 增加伪造 replay、重复提交、跨玩家 matchId、重启后一致性测试。

### P0-02：修复 PVP 奖励 outbox，保证真实入账

问题：结算生成 `pending` 奖励，但生产环境没有消费者，honor/gold 不会进入玩家账户。

实施要求：

- 增加常驻或可恢复的 outbox worker；
- worker 使用 claim → apply → complete/fail 状态机，带 lease、重试、退避和幂等键；
- 奖励应用必须以 `rewardEventId` 做 exactly-once，不能因重试重复发放；
- worker 启动时扫描历史 pending，停机时安全释放 lease；
- 增加 pending、failed、retrying、dead-letter 指标和告警。

验收标准：

- 一场 PVP 结算后 honor/gold 在玩家账户真实可见；
- worker 重启、网络失败、重复消费均只入账一次；
- pending 事件最终进入 complete 或可审计的 failed/dead-letter，不得永久悬挂；
- 增加完整 PVP settlement → outbox → account E2E。

### P0-03：修复 PVP load-failed 的 no-contest 结算与回收

问题：failed load ACK 将 runtime 置为 `voided`，但绕过结算；后续 tick 又跳过该 runtime，最终不产生历史记录，也不被 reaper 回收。

实施要求：

- failed load ACK 必须立即进入统一 settlement 流程；
- 定义明确的 `no_contest`/`load_failed` 结果、原因、责任方和奖励策略；
- `voided` 不得被当成“无需结算”的 quiescent 状态，除非已有 immutable settledDetail；
- reaper 按 terminal 状态和 TTL 回收，但保留可审计的结算摘要；
- 增加重复 ACK、双方同时失败、一方失败一方成功、服务重启恢复测试。

验收标准：

- failed load 后产生唯一 no-contest 结算记录；
- 5 个以上 tick 后 live match、custom room 和运行时均可回收；
- 不会产生普通胜负、平局或未结算假记录；
- 同一 requestId 重试不重复结算。

### P0-04：修复 PVP 活动对局跨进程恢复

问题：进行中的比赛、自定义房和订阅只存于进程内 Map，新进程无法恢复。

实施要求：

- 为 loading/playing/terminal 前的活动对局持久化 checkpoint 或 event journal；
- 启动时恢复 custom room、participants、runtime phase、tick、双方状态和 command receipts；
- 恢复必须校验规则版本、schema 版本和数据完整性；
- 进程迁移期间禁止两个实例同时推进同一 match，增加 lease/fencing token；
- 结算和奖励 outbox 必须与恢复后的 match 继续幂等。

验收标准：

- 实例 A 创建并推进对局，实例 B 接管后可继续同一 match；
- 重启前后 matchId、phase、tick、玩家状态和下一动作一致；
- 双实例竞争时只有一个 owner 能推进 tick；
- 增加真实进程重启、故障转移和恢复哈希测试。

### P0-05：修复 PVP 断线裁决和后台标签页语义

问题：错峰双断线可能把先确定败局变成平局；后台页面关闭 SSE 后会被直接判负。

实施要求：

- 断线裁决按“先达到断线宽限期限的一方先结算”，不得等待另一方也超时后改判平局；
- 明确 disconnect、background、network handoff、page unload 的不同语义；
- 前端切后台不应主动中止唯一权威连接；若浏览器限制连接，服务端应使用 grace/heartbeat 状态而非立即判负；
- 恢复连接后使用 generation/fencing 校验，旧连接不能覆盖新状态；
- 增加生产级 60 秒后台、错峰断线、丢包、刷新和网络切换 E2E。

验收标准：

- A 先断线并到期，B 未断线时结果确定为 A 负；B 随后断线不改写结果；
- 后台超过 60 秒但连接/心跳仍有效时不误判败北；
- 连接恢复不能重复结算或覆盖已结算结果；
- 20 局基础 E2E 与新增长时场景全部通过。

### P0-06：密码房必须真正校验密码

问题：当前只保存 `hasPassword`，加入协议不读取或校验密码，密码房等同公开房。

实施要求：

- 房间保存密码哈希、算法版本、salt 和更新时间，不保存明文；
- `CREATE_ROOM` 返回 `hasPassword`，不返回哈希；
- `JOIN_ROOM` 和 REST join 必须携带 password proof，并在服务端验证；
- 错误密码、缺失密码、重复尝试要返回结构化错误并限流；
- 日志、回放、快照和客户端状态禁止泄露密码或哈希。

验收标准：

- 正确密码可加入；错误或缺失密码返回 401/403，不占用槽位；
- 无密码房仍可正常加入；
- 重启后密码验证仍有效；
- 增加暴力尝试限流与审计测试。

### P0-07：实现双方独立的 PVP 随机袋

问题：PVP runtime 共用全局 PRNG，一方额外征兵会改变另一方结果。

实施要求：

- PRNG 按 matchId + side/playerId + bagIndex 派生独立种子；
- 所有征兵、洗牌、掉落和 pity 随机均从对应 side 的随机上下文读取；
- 将随机状态纳入 checkpoint/replay，保证重放确定性；
- 禁止客户端提供随机种子覆盖服务端结果。

验收标准：

- Alice 多征一次不改变 Bob 下一次结果；
- 相同 match seed、相同 side 操作序列可重放得到完全相同结果；
- 不同到达顺序不会改变对手随机袋；
- 增加公平性和回放测试。

## 4. P1 功能实装项

### P1-01：武器效果必须“全部接线或全部隐藏”

现状：41 件武器中完整生效 16 件、部分生效 3 件、完全未接线 22 件。空壳清单和机器矩阵见：[weapon-runtime-report.json](/Users/yueyue/AI项目/A2A/AgensTD/output/functional/weapon-runtime-report.json)。

实施要求：

- 为每件武器建立 `declared effect → runtime handler → combat event` 映射；
- 优先实现 22 件空壳的核心效果，至少覆盖属性修改、普攻触发、主动技能触发、状态、额外目标/伤害等声明类型；
- 对贯日弓、混元伞、玲珑宝塔补齐未接线效果，或删除/改写 UI 文案为实际效果；
- runtime 遇到未支持效果不得静默；测试环境必须有结构化错误，生产环境必须从目录/API 隐藏；
- `status=testing` 的内容不得进入正式玩家可获得列表，除非明确开启内部测试开关；
- 给有组合限制的武器配置 `uniqueGroup`，并保留服务端冲突校验。

验收标准：

- 每件可见武器至少有一条真实 runtime 事件证明其声明效果生效；
- 不允许出现 `WEAPON_EFFECT_UNSUPPORTED` 而 UI 仍宣称完整效果；
- 41 件武器逐件矩阵通过：目录、图片、兼容性、合成、装备、快照、战斗效果；
- 双武器属性叠加和专武追加伤害保持正确；
- uniqueGroup 至少有真实配置并能触发冲突拒绝；
- 完成 41 件武器回归测试后才可开放全部武器。

### P1-02：补齐 4 个主动道具真实成功/失败分支

未获得真对局成功证据的主动道具：神将符、招魂幡、定风符、战鼓令。

实施要求：

- 为每个道具准备合法目标、非法目标、错误阶段、冷却中、次数耗尽、重复 requestId 场景；
- 成功路径必须产生权威事件、更新 charges/cooldown/runtime version；
- 失败路径必须 no-consume，返回可理解的错误；
- 前端在目标选择、取消、错误和服务端确认期间保持状态一致；
- 修为丹需补做真 UI 合法神将目标成功分支，不只依赖 runtime smoke。

验收标准：

- 8/8 主动道具都有浏览器真实成功和失败证据；
- 每次成功最多扣一次；重复 request 不重复施加效果；
- 道具效果可在权威状态和事件流中观测；
- UI 只在服务端确认后扣除次数。

### P1-03：首次教学必须保证玩家能完成基本操作

问题：教学卡片在前景显示时，PVE 战斗仍按正常速度推进，真实测试中玩家可能在完成教学前因敌军超载败北。

实施要求：

- 首次进入 PVE 使用服务端 prep/tutorial phase，至少保证召唤、选择托盘、部署一次和使用一次道具；
- 教学期间禁止超载败北，或显著延长第一波准备时间；
- 教学完成/跳过后再恢复正常波次计时；
- 教学状态必须服务端可恢复，刷新页面不能重复扣资源；
- UI 明确显示“教学中/战斗暂停/可跳过”状态。

验收标准：

- 新账号首次流程在正常网络下至少完成一次召唤、部署和一个道具动作；
- 教学未完成时不会因超载直接败北；
- 跳过教学后进入标准 PVE 规则；
- 增加慢网络、刷新、断线恢复和移动端教学 E2E。

### P1-04：修复武器构筑保存后的神将选择重置

问题：选择后羿后执行合成或保存，页面刷新状态跳回列表第一名杨戬，数据虽保存但操作上下文丢失。

实施要求：

- mutation 前保存 `selectedGeneralId`；
- refresh 后按 ID 恢复选择，若角色已不可用才回退到第一项；
- loading 状态不要卸载整个 ArsenalView，或把选择状态提升到稳定父级；
- 增加键盘焦点恢复和移动端滚动位置恢复。

验收标准：

- 后羿合成、保存、刷新后仍选中后羿；
- 失败请求也不跳回杨戬；
- 账户版本更新和视图选择状态独立验证。

## 5. P1 运行稳定性与资源治理

### P1-05：自定义 PVP 同一玩家只能有一场活动对局

实施要求：

- create/join/ready/start 全路径检查 active match；
- 使用持久层或分布式锁保证并发下只有一个 match；
- 已有活动对局时返回结构化 `ACTIVE_MATCH_EXISTS` 和可继续入口；
- no-contest/settled 后再释放锁。

验收标准：同一玩家并发提交两个房间 ready，只有一场进入 loading/playing。

### P1-06：房间与命令接口增加幂等、限流、配额和 TTL

实施要求：

- 创建房间、加入、ready、命令接口消费 requestId；
- 同一 requestId + payload 返回同一结果，不重复创建资源；
- 按用户/IP/房间增加速率限制和最大并发房间数；
- 空房、未开始房、终态房分别配置 TTL；
- 定期回收 tickets、acceptedMatches、commandReceipts、SSE 订阅和房间索引。

验收标准：同一 requestId 重试 20 次只创建一个房间；空房按 TTL 回收；洪泛测试不会无界增长。

### P1-07：修复 PVP SSE 错误响应顺序

问题：SSE 在校验 match/参与者前先发送 200 headers，后续 403/404 只能断连接并产生日志错误。

实施要求：先完成鉴权、match、participant 和权限校验，再 flush headers；错误统一返回 JSON/结构化 SSE error。

验收标准：陌生人访问、未知 match、已结束 match 均得到正确状态码和错误体，无 `Cannot set headers after they are sent`。

### P1-08：补齐服务配置边界校验

实施要求：对 port、tick、地图尺寸、rate limit、replay 容量、TTL、广播间隔等配置验证正数、整数、上下限和相互关系；非法配置启动时 fail-fast，并输出变量名和允许范围。

验收标准：NaN、负数、0、超大值、浮点值和互相矛盾配置均被拒绝；合法默认配置保持现有行为。

## 6. P1 发布工程与前端质量

### P1-09：修复前端 CI 图片预算误报

问题：构建产物实际有图片，但预算脚本将动态模板变量 `art/equipment/${s}.webp` 当作文件名，导致 `pnpm test:ci` 稳定失败。

实施要求：

- 图片扫描器识别并忽略动态模板字符串，或在构建阶段输出真实 manifest 后校验 manifest；
- 保留真实缺图检查，不能简单关闭脚本；
- 为动态 import、CSS url、public 资源增加 fixture。

验收标准：真实缺图会失败，现有合法构建不误报；`cd FE && pnpm test:ci` 全绿。

### P1-10：修复 `dev-stack.sh` 一键启动

问题：README 指定的 `./dev-stack.sh start` 会把 `SUPABASE_URL=` 当成命令执行，后端立即退出。

实施要求：使用数组参数或 `env VAR=value command` 正确传递环境变量；启动失败时输出真实子进程日志并清理残留 PID。

验收标准：全新终端执行 README 命令可启动前后端、健康检查通过、stop 可清理所有进程；空 Supabase 配置也能进入内存测试模式。

### P1-11：补齐前端 dialog、键盘和移动端无障碍

实施要求：

- PVE/PVP 创建房间、投降确认等弹窗使用 `role=dialog`、`aria-modal=true`、标题关联、初始焦点、焦点圈定和 Escape 关闭；
- 删除嵌套交互控件：不要在 `article role=button` 内再放同动作 button，不要在 weapon slot button 内嵌无名称 `role=button`；
- 移动端图标导航补充稳定 `aria-label`，不要因 CSS 隐藏唯一文本而变成空名称；
- 异步错误使用 `role=alert` 或 live region 主动播报；
- 修复登录页 390px boot log 裁切和 Arsenal 超长页面滚动体验。

验收标准：键盘 Tab 顺序不进入背景控件；Escape 可关闭弹窗；390px/430px 关键页面无空名称、横向溢出和不可达 CTA；读屏可识别所有导航与错误。

## 7. P2 数据、生命周期与一致性

### P2-01：优雅关机保存最终 PVE checkpoint

实施要求：SIGTERM/SIGINT 时先停止接收新动作，再 flush 最终 PVE checkpoint 和 replay，等待持久化结果后退出；失败要记录并返回非零状态或进入重试。

验收标准：关机前后恢复的 tick、棋子、敌军、资源和事件哈希一致，不回退默认 50 tick 周期。

### P2-02：为收据、匹配和订阅建立淘汰策略

实施要求：acceptedMatches、tickets、commandReceipts、SSE subscribers、old generations 设置大小/时间上限；已结算数据转持久摘要，内存只保留必要窗口。

验收标准：长时间运行和 1000+ 唯一 requestId 压测内存稳定，查询不会线性恶化。

### P2-03：前端 bundle 与运行时资源预算

实施要求：Phaser 当前 gzip 约占预算 95.8%，禁止继续无门槛增加包体；大型武器目录采用虚拟列表/分页或延迟加载；VFX、DOM、事件批处理保持现有压力测试水平。

验收标准：桌面和移动端构建均在预算内；80 活跃敌人/300+ 战斗事件压力场景保持 0 long task，且不出现明显内存增长。

### P2-04：真实 Supabase staging 门禁

实施要求：在隔离 staging 项目执行 migration、RLS、RPC、schema drift、并发结算、故障切换和 outbox 入账；禁止只做静态 SQL 解析。

验收标准：migration 可重复执行且无漂移；匿名、人类、Agent、跨玩家读写权限符合预期；真实网络故障和恢复有可审计结果。

## 8. 数值与关卡门禁

### P2-05：将 full-build balance 纳入发布门

问题：快速 balance smoke 中多个难度均 512/512、100% 通关，不能证明难度梯度；真正的 `test:balance:full` 运行时间长且无中间进度，当前 `release:verify` 没有执行它。

实施要求：

- 将 full-build balance 拆成可并行、可报告中间进度的任务；
- 明确 easy L1、easy L10、normal L10、hard L1 的目标通关率区间；
- 输出构筑、波次、Boss、经济、失败原因和随机种子；
- 将结果纳入 release gate，但允许 nightly 与 PR 快速门分层；
- 若真实玩法与模拟器结果偏差，优先修复模型或统一规则来源。

验收标准：PR 门有快速确定性 smoke，nightly/release 门有 full-build 数值矩阵；失败时能定位到具体波次、敌人、构筑和种子。

## 11. 完成定义（Definition of Done）

每项修改只有同时满足以下条件才能标记完成：

1. 代码实现已合并，未通过删除校验或放宽断言解决问题；
2. 有对应的成功、失败、重复请求、刷新/重启场景；
3. 权威状态、事件、数据库记录和 UI 展示一致；
4. 有自动化回归命令和产物路径；
5. 明确性能、资源和安全影响；
6. 旧数据迁移、回滚和兼容策略已写明；
7. 相关 P1 复现不再成立，且没有引入新的 console error、无障碍回归或内存泄漏。
